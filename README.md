# 炭焙三维复现与焙火记录系统

浏览器内的铁观音炭焙过程三维复现 + 逐颗粒焙火追溯系统。纯 TypeScript + 手写 WebGL2 着色器，
零三维引擎依赖；批次与焙火数据存 IndexedDB。

## 启动

```bash
npm install
npm run dev        # http://127.0.0.1:5180
```

首次打开会自动生成种子数据（3 个毛茶批次、2 个焙窟、3 位师傅、4 条焙火记录），
并对每条记录的 5000 颗颗粒跑完整炭焙仿真后落库。清空 IndexedDB 后刷新可重新生成。

## 校验脚本

```bash
npm run check          # 类型检查 + 路由 + 无头仿真 + 渲染热路径性能
npm run check:sim      # 4 条种子记录的档位/焦损/排列合法性
npm run check:perf     # 5000 颗粒逐帧 CPU 组装与翻焙性能
npm run build          # 生产构建（gzip 后约 29KB）
```

## 五个页面

| 页面 | 能力 |
|---|---|
| 毛茶批次 | 品种/山场/做青/含水率/紧结度登记，投茶量+笼径自动算铺茶厚度 |
| 焙笼配置 | 焙窟实际尺寸、炭种炭量、盖灰厚度；三维看炭面中心→边缘温度分布，灰越厚越平 |
| 焙火记录 | 全部批次档案总表，进入三维焙火的入口 |
| 焙火过程 | 时间轴仿真、翻焙/压灰节点增删改、手写记录文本解析录入、剖面、颗粒追溯 |
| 成茶对比 | 两笼并排、火功均匀度直方图、上中下层差、轻/中/足三档对标、复焙前后对比 |
| 师傅档案 | 招牌曲线存档、新人照老师傅曲线焙的逐节点偏差提醒 |

## 关键设计

### 逐颗粒身份与翻焙不丢不重
每颗茶有恒定 id（=初始槽位）。`slotOf[id]` 记录当前槽位，翻焙时对槽位做一次 Fisher–Yates
洗牌得到排列 `perm`，再 `slotOf[id] = perm[slotOf[id]]`。排列在引擎内用 `assertPermutation`
校验，无头测试对每次翻焙都验证是合法排列（5000 个槽位一一映射）。点任意颗粒都能按 id 调出
从进笼到出焙的完整温度/火功历程，翻焙只换槽位、不换身份。

### 火功与焦损（`src/sim/temperature.ts`，经验公式可解释）
- 炭面中心温度由火力与盖灰厚度决定，盖灰按指数削峰；径向用高斯衰减，灰越厚梯度越平。
- 颗粒温度对环境温度做一阶滞后（τ≈75s，茶是热的不良导体）。
- 累计火功 = ∫(T−80)² dt，按厂内三档标定：`<0.62 轻火 / <1.25 中火 / ≥1.25 足火 / ≥1.8 过火`。
- 焦损只在 >138℃ 累积，底层有额外加成，因此"翻焙不及时底层焦掉"可复现。

### 5000 颗粒实时渲染
单次 `drawElementsInstanced` 画全部颗粒（7×10 低面数球 + 程序化皱缩），每帧只更新 5 个实例
缓冲。实测 CPU 侧组装 2.7ms/帧（约 370 FPS 上限），颗粒颜色/焦斑/油润全在片元着色器里按
逐颗粒 heat、scorch 计算，零 JS 颜色计算。点选用离屏 FBO 编码颗粒 id 到 RGB。

### 数据体量
历程按 120s 间隔列式采样（`histTimes/histTemp/histHeat`），摊凉期不采样。一条 6 小时、
5000 颗粒的记录约 5–9MB，带 3 天摊凉+复焙的长记录也控制在同量级。

## 种子数据里的救场案例

R003（吴阿炭，跟随陈德炉曲线）：起炭偏猛、盖灰仅 1.2cm，75 分钟时笼壁烫手，紧急压厚灰到
4.6cm 并撤火。仿真结果是整体救回中火档，但前段高温已造成约 60% 颗粒起焦斑——
"救回来但留了痕迹"，师傅档案页会标出与老师傅曲线的全部偏差节点。
